# 01 Pick a better small model than Qwen 0.5B

Status: needs-triage
Type: research

## Context
Qwen2.5-0.5B is much weaker than Jev (low and unstable confidences). Recommendations were given in conversation but no decision was made.

## Options
- Write a comparison script over the labeled set (`evals/run_eval.py` runs any backend over it, see label-evaluation/08a; use `--backend hf --split tuning heldout --save <name>` and `--compare`) and run several candidate models.
- Try Qwen3-1.7B, which needs a higher `mem_limit` than 4 GB in `compose.yaml`.
- Keep Qwen for tests and use `JEV_BACKEND=jev` for real use.

## Done when
A model is chosen with accuracy numbers, or the decision is recorded to stay with the hosted backend.

## Constraint (owner, 2026-10-11)
Larger local models are much slower, and the service runs on a VPS that may not be able to accommodate them. A model therefore has to fit the VPS's memory and answer fast enough, not only be accurate.

## Comments

> *This was generated by AI during triage.*

**What we know so far:**
- The harness already prints classification time and saves it with each run (`evals/results/*.json`), so one run gives accuracy and speed together.
- The service asks three questions per ticket, so a batch of N tickets costs about 3N model calls. Slowness grows with both model size and batch size.
- On the hosted backend, 12 tuning tickets took about 3 seconds in total (see `evals/results/after-label-fix.json`).
- The local Qwen2.5-0.5B has not been scored on the labeled set yet.

**Recommendation:** treat speed and memory as pass/fail limits, and accuracy as the ranking. A candidate must first fit the VPS and meet the time limit, and only then is it ranked by held-out accuracy. If no local model passes both, record the decision to stay on the hosted backend (the third option), which is likely given the VPS.

**What we still need from you (owner):**
- The VPS size: how much memory and how many CPU cores it has, and whether it has a GPU.
- The slowest acceptable response, for example for a batch of 10 tickets.

> *This was generated by AI during triage.*

**VPS facts and limit (owner, 2026-10-11):** 15 GiB memory (about 8.8 GiB free while other services run), 10 CPU cores, no GPU, no swap. The speed limit is 2 seconds per ticket.

**Measured, same 30 tickets (12 tuning, 18 held-out), saved in `evals/results/`:**

| | Hosted Jev (`after-tuning`) | Local Qwen2.5-0.5B (`hf-qwen25-05b`) |
|---|---|---|
| Time per ticket | about 0.2 s | about 5.9 s (178 s for 30) |
| Held-out severity / category / team | 62% / 94% / 94% | 44% / 44% / 44% |
| Tuning severity / category / team | 44% -> 78% (before the relabel) | 44% / 44% / 11% |

- The smallest local model is already about three times over the 2 second limit, and its held-out accuracy is far below the hosted model on every question. Its team answers on the tuning set are almost always wrong (1 of 9).
- A larger local model will be slower than 5.9 s per ticket on this CPU, and a 1.7B model would also need more than the 4 GB `mem_limit`. Neither limit can be met by going up in size.
- Caveat: the run shared the machine with other services (about 6.8 GiB in use), so the time may be somewhat pessimistic. It would have to be about three times faster to meet the limit.

**Recommendation:** record the decision to stay on the hosted backend (`JEV_BACKEND=jev`) for real use and keep Qwen only for tests and offline smoke runs. Revisit only if the VPS gains a GPU or the 2 second limit is relaxed. Move to `resolved` on the owner's confirmation.
